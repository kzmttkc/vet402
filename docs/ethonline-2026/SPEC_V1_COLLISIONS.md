# 製品定義書 v1.0（VET402-SPEC-1-2-2026-08-31）と会期の衝突点

> グラント戦略セッションが 2026-09-01 に定義書を全文読んで作成。**実行はハッカソン戦略セッションが持つ。**
> 前提: 大型更新は 2026-09-02 に入る。タグ `pre-ethonline-2026` は 09-03、会期は 09-04→09-13 12:00 EDT。

## 1. 定義書の中核が、会期で作る動詞そのもの（最優先）

§8.3 `/decision`（支払前に ALLOW/WARN/BLOCK）と §9.3 のミドルウェア既定
——「買い手モード: リクエスト前に `/decision?role=payer`。BLOCK/未検証は送金しない」「失敗時 fail-closed」
「SDK既定は allow-only（WARN/BLOCKは払わない）」——は `payOrRefuse` と同一物である。

9/2 に main へ入れば、**09-04 の開始時点で動詞は既に存在する**。Continuity で「会期中に作った」と言えるものが消える。

**9/2 のマージ前に決めること**: 仕様のどこを会期用に意図的に残すか。
推奨は **会期の新規を Hedera レーンへ移す**こと。狙う賞（Hedera「AI & Agentic Payments」$6,000）の要件は
*Hedera 上に x402 ゲート付きサービス＋Blocky402 経由の実有償リクエスト1件* で、定義書の対象外
（§7.1 のチェーンは Base / Solana / Polygon、追加は「アダプタ」）。
**Base側の `/decision` は会期前の既存機能として開示し、会期の新規は Hedera 実装**。どちらも事実に反しない。

## 2. ERC-8004 Validation 書き込み（§11・P1）は凍結中の動詞

Mumbai（11-06）の目玉が「空の Validation Registry を埋める」。P1 が早く入って本番で書き始めると先に消化される。
§11 自身が「既定のオンチェーンアンカーはフラグOFFを維持してよい」と書いている。
**Validation 書き込みの本番ONは 11-06 以降に固定する。**

## 3. ブランチ衛生

- 会期中（09-04〜09-13）は **main → `ethonline-2026` のマージをしない**（GIT_RULES）。
- `pre-ethonline-2026` タグは **9/2 の更新が入った後**（予定どおり 09-03）に打つ。
  これで今回の大型更新は「持ち込み」として明確に線引きされる。順序自体は正しい。

## 4. 数字の定義が変わる（§7.2）

wash/test 除外後を「実需」と呼ぶ規定により、**vet402 自身の購入は `test` として実需から外れる**。
現在公開・提出済みの数字（L1 attempts / settled）は全てその自社購入である。
提出済みの Base 指名（2026-08-25）・Octant intake（2026-08-27）・`/demo` の字幕は旧定義で書かれている。
§7.2 の「混ぜて一つの数字にしない」に従い、**画面と申請文で新旧どちらの定義かを必ず言い分ける**。

副作用: 執行部の L1 欠測カナリア（`Takeshi_Automation/scripts/vet402_l1_canary.py`）は
「毎日1バッチで約100行」を前提にしている。§7.4 の階層化（C2 は24時間ごと・バジェット超過でサンプリング）と
§6.2 の「同一測定ウォレットは1時間1回」で挙動が変わる。**更新後にグラント側が閾値を見直す。**

## 5. §12 のリリース凍結条項

「Accuracy ledger に週次で出せない週はリリース凍結」。09-11〜09-13 は収録と提出の直前で、
**凍結が発火すると提出物の修正を出せない**。会期の10日間だけ、凍結条件の扱いを事前に決めておく。

## 6. 参考: 定義書と会期の相性が良い点

- §9.2「既存エンドポイントは維持する。互換を壊す変更は `/api/v2`」——公開済みリンクとデモは壊れない。
- §10 の証拠規則（tx_hash・再現手順が無い失敗は公開しない）は、提出物の主張の裏取りにそのまま使える。
- §13「測定ウォレットは公開する」は、審査員が我々の購入をチェーン上で追える形になる。
