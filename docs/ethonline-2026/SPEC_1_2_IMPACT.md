# 製品定義書 v1.0（VET402-SPEC-1-2）が ETHOnline に与える影響

> 2026-09-01。対象文書: `vet402-product-requirements-spec.docx`（版1.0・2026-08-31・全353段落を読了）。
> **大型アップデートは 9/2 に入る。ETHOnline の会期は 9/4 00:00 UTC 開始、タグは 9/3。**
> このファイルはハッカソン戦略セッションの所見であり、製品仕様の是非は論じない。
> **仕様そのものは良い。**問題は「いつ入るか」だけである。

---

## 0. 決定（2026-09-01・Takeshi 承認済み）

**全体を会期後へ後ろ倒しにはしない。遅らせるのは1項目だけ。**

| いつ | 何を |
|---|---|
| **9/2 予定どおり** | 仕様の **P0 全部**（同一IDモデル・`/resolve` と逆引き・決済索引と wash 分類・カバレッジ階層・異議と訂正ログ・Accuracy ledger）＋ **`/decision` API 本体**（判定を返すだけ）＋ **売り手モード** |
| **9/4 00:00 UTC 以降** | **§9.3 の買い手モードだけ**——「リクエスト前に `/decision?role=payer`、BLOCK/未検証は送金しない」。これが会期の新規そのもの |
| 進めてよい（動詞を1つ失う選択） | §11 Validation Registry 書き込み（P1）。Mumbai は既定 No-Go なので製品を優先する |

**理由**: 到達可能な賞金は最大 $8,500 で、期待値はよくて数百〜千数百ドル。
一方この仕様は「買い手向けAPIが誰にも WARN しか返せない」という**金に一番近い段の詰まり**を直す。
売上ゼロの会社がその解消を2週間遅らせて宝くじを買うのは順序が逆。
**買い手モードだけは、2日早く出しても製品価値がほぼ増えず、2日待てば提出物の中核が残る**——
そこだけを遅らせる。仕様自身がこれを P1 に置いており、9/2 を P0 に留めれば衝突しない。

**既存が厚いことは減点ではない。** 審査が見るのは「本物の製品が、この会期で意味のある1歩を進めたか」。
薄い土台＋新しい動詞より、厚い土台＋鋭い動詞のほうが強い。

**9/2 のリリースに付ける3条件**: (1) `signals.receiving` のフィールド名と意味を変えない
（変えるなら SDK の evidence floors も同時に）(2) リリース後に本番の健全性を実測してから 9/3 のタグ
(3) 9/3〜9/13 は不具合修正以外を本番に入れない。

## 1. 最重要: 会期の新規が消えかねない箇所が2つある

Continuity は**会期中の差分だけ**が賞の対象で、会期前に入った実装は「既存」として開示される。
2026-08-25 に evidence policy で実際にこれが起きた（`AGENTS.md` 最上部のフリーズ参照）。

### (A) §9.3 ミドルウェアの買い手モード ＝ `payOrRefuse` とほぼ同一

> 買い手モード: リクエスト前に対象Resourceを `/decision?role=payer`。**BLOCK/未検証は送金しない**
> 失敗時 fail-closed。タイムアウトは BLOCK 相当。**サイレント通過禁止**

これは会期中の新規である `payOrRefuse` の中核と**同じ振る舞い**である。9/2 にこれが入ると、
提出時に「今週作った」と言えるものが**ほぼ残らない**。

**要求**: 9/2 のリリースに**買い手側の「払う前に止める」経路を含めない**。
含めてよいのは `/decision` API 本体（判定を返すだけ）と**売り手モード**（受領後に payer を判定）。
買い手側で署名前に止める配線は **9/4 00:00 UTC 以降**。
（仕様 §14 でも買い手モードへの切替は **P1** であり、P0 ではない。P0 に留めれば衝突しない。）

### (B) §11 ERC-8004 Validation Registry への書き込み ＝ **Mumbai の動詞**

3連戦は「大会ごとに新しい動詞を1つ」で設計してあり、**Mumbai（11/6–8）の動詞は Registry への本書き込み**。
仕様は §11 でこれを P1 に置き、「空の Validation Registry を埋めることがポータブル2の完了条件」とする。

**判断が要る（私の推奨: 製品を優先して書き込みを進める）**:
Mumbai は既に**既定 No-Go**（賞ページ未公開・continuity 枠の有無が不明・判定日 9/20）。
賞のために製品の完成を遅らせるのは順序が逆である。**Registry 書き込みは仕様どおり進めてよい。**
ただしそれは **Mumbai の動詞を失う**という選択なので、意識して選ぶ。
Mumbai に出す場合の新規は別途立てる（例: 書き込みではなく**第三者が検算できる形での検証**）。

## 2. 会期の実装が壊れうる箇所（9/2 後に必ず再測）

### (C) §8.3 の判定関数が **ALLOW を出せるようにする**

> ALLOW if l0 == pass and (l1.n_delivered >= 1 or operatorがL1なしALLOWを明示オプトイン) and l2 != mismatch

現行本番は **ALLOW が構造的に出ない**（受領実績の無い payee は thin ceiling 69 で頭打ち・
[`fixtures.md`](./fixtures.md)）。新しい関数では **L1 配達が1件でもあれば ALLOW** になりうる。

影響:
- **動画の核心が変わる**。今の絵は「既定 policy ではカタログ全体が止まり、根拠を名指しした1件だけ通る」。
  ALLOW が普通に出るなら、`allow-only` でも通ってしまい、**対比が消える**。
- C1 リハーサル（[`rehearsal-c1.md`](./rehearsal-c1.md)）の5ケースは**全て再実行**が要る。
- 拒否側フィクスチャ（`agent.api.0x.org`・L1 実績0件）は、§8.3 では
  `l1.n_attempts >= 3 and n_delivered == 0` に当たらないので **BLOCK ではなく WARN**。
  「証拠が無いから払わない」の絵は policy 側で作る（変わらず成立する）。

**要求**: 9/2 のリリース後、**9/3 のタグ前に C1 を再実行**し、結果をこのファイルに追記する。
数字も絵も、リリース後の実測で入れ替える。

### (D) §9.2 スコアAPIが「薄い互換レイヤ」になる

> スコア系は decision の上に薄い互換レイヤとして残す。新規統合は `/decision` を正規とする。
> `trustScore` を L0–L2 フィールドに入れて返すことを禁止する。

会期の実装（および 8/25 に入った evidence policy）は `GET /payees/{addr}/score` の
`signals.receiving`（`l1DeliveryCount` 等）を読む。**このフィールドが動くと SDK が黙って壊れる。**
現時点の実測では `signals.receiving` は trustScore とは別のオブジェクトなので、仕様の禁止事項には触れない。

**要求**: 9/2 のリリースで `signals.receiving` の**フィールド名と意味を変えない**。
変えるなら SDK 側の evidence floors を同時に直す（両方 9/4 前に終わらせるか、両方 9/4 後にする）。

### (E) §7.2 wash/test 除外で**公開数字の定義が変わる**

> 公開合計から wash / test を除外した値を「実需」と呼ぶ。除外前の生値も出す。

vet402 自身の L1 購入は `test` 扱いである（§7.2 の wash_flag に「既知の測定ウォレット（vet402自身を含む）」）。
つまり**「実需」からは我々の購入が除かれる**。動画や提出物で数字を語るとき、
**どちらの数字を言っているのか**を混ぜない。我々の測定実績（2,018 試行 / 902 成立）は
「vet402 が自腹で測った回数」であって「市場の実需」ではない。

**要求**: リリース後、公開面の数字がどちらの定義で出ているかを確認してから台本の数字を確定する。

## 3. 賞にとって追い風になる箇所

- **§9.1 `/decision` が facts と recommendation を同じレスポンスで返す**（`facts` 省略モードは禁止）。
  「スコアだけ返す不透明な API」ではないことが仕様で保証される。審査で効く。
- **§10 証拠規則**（tx_hash・再現手順が無い失敗は公開しない）と **§12 SLO**（自社の誤判定率を出す）は、
  「測る側を測る」という我々の一貫した主張の裏付けになる。
- **§7.3 逆引き**（payee → endpoints、tx → resource）は、The Graph 枠で
  「Subgraph の生データと自社台帳を突き合わせる」実装の土台になる。

### リリースで直した本番の欠陥（仕様と別に実測で見つかったもの）
