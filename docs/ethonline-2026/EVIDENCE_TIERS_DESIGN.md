# Evidence Tiers — 判定の証拠を等級化する設計（2026-08-26）

> 状態: **設計のみ**（9/13 提出まで実装しない・ROADMAP §5 の凍結を守る）。
> 目的: 堀・判定エンジン・市場での主張の3つが、共通の1つの欠陥から出ていることを
> 直す。欠陥とは「**証拠に等級が無い**」こと——偽造不能な決済確認と、売り手が
> 制御できる本文チェックが、同じ `delivery_verified` に潰れている。
> 全数値は 2026-08-26 の本番実測（Neon `vouch`・読み取りのみ）。

## 1. なぜこれが根なのか

外部レビュー（2026-08-26・2本）が3つの前提を崩した後の再診断:
- 失敗台帳は堀と呼べる厚みがまだ無い（真の売り手起因不履行は全台帳で **50件**）
- L2配送検証の現行定義（HTTP 200 + 本文非空）は**売り手が制御できる**——
  `{}` を返すだけで通る（コードレビュー C-1）
- 「trust の先行者」は張れない（本家の隣人が全員 trust 隣接）

生き残る非対称は1つ。**「決済がオンチェーンで起きた」＋「宣言どおりの品が実費で
届いた」を同時に持つ記録**は、ファシリテータ（決済しか見えない）にも評判集計
（自分で買わない）にも作れない。だが今それは1つの真偽値に潰れていて、
強い証拠と弱い証拠が区別できない。等級化がその修復。

## 2. 等級の定義と現在の実数（本番 2026-08-26）

| 等級 | 定義 | 実数 | 偽造耐性 | 誰に見えるか |
|---|---|---|---|---|
| **E0** | 決済をオンチェーンで再読し確認（宛先・金額・トークン・チェーン・確定数≥32） | 653 | 偽造不能（チェーンが証人） | ファシリテータも見える |
| **E1** | E0 ＋ 有料応答が 200・本文非空・content-type 一致 | 639 | 弱（売り手制御下） | 買った者のみ |
| **E2** | E1 ＋ **宣言スキーマと実応答が一致**（`l2_schema='match'`） | **214** | 中（宣言との自己拘束） | 買った者のみ |
| **E3** | E2 ＋ 独立した第三者 buyer の署名 attest | 0（未来） | 強（funder-collapse で防御済み） | ネットワーク全体 |

反対の証拠（負の等級）も同じ台帳から出る:
- `l2_schema='mismatch'`（宣言と違う品を返した）: **29 売り手**
- 売り手起因不履行（5xx + 決済後3状態）: 50 件

## 3. E2 は「核」と呼べるか（反証条件の検証）

私が挙げた反証条件「E2 が特定売り手に偏れば核と呼べない」を実測でクリア:
- E2 を持つ売り手 **37**（214件が分散・最多でも 43件＝20%）
- 「E2 が3件以上 かつ 売り手起因不履行0」の **ALLOW 候補が14売り手**

→ 214件は空論でなく、**今日から運用可能な核**。動画で「1人だけ通す」にも
14人の母数がある。

## 4. 段階的な適用（時期を分ける）

### 段1（会期前・凍結安全圏・開示のみ）
スコアの意味論を1バイトも変えず、**等級の件数を機械可読で開示**する。
`signals.receiving` に `l1EvidenceE0/E1/E2` と `l2MismatchCount` を足す
（スキーマパリティ4面で強制）。ALLOW を出さなくても、
「48件が E2 で不履行0の売り手」と「653件中 mismatch 多数の売り手」を
**呼び手が区別できる**ようになる。9/3 のフィクスチャ凍結を壊さない。

### 段2（9/13 提出後・正しさの未済バッチ）
監査で確定済み・設計不要・実装のみ:
- 時間減衰（H-8。`lastPaymentAt` は計算済みで未使用）
- outcome-detector の USDC leg（USDC専業売り手が恒久 dormant）
- cache epoch の発火漏れ（M-2）

### 段3（9/13 後・ALLOW の再設計）
退避した evidenceBasis パッチ（`output/0826/evidence-basis-WIP-2026-08-26.patch`）を
土台に、C-1/C-2 を塞いだ形で:
- 自社台帳 ALLOW の配送証拠は **E2 のみ**を数える（E1 は数えない＝C-1 の
  「本文1バイトで通る」穴を塞ぐ）
- `l2_schema='mismatch'` は**減点側**に数える（C-2 の「空を返す売り手が
  ALLOW を保持」を塞ぐ）
- 鮮度14日＋`evidenceBasis` 開示＋呼び手の `requireEvidenceBasis` 拒否権
- **残存リスクは開示で処理**: 緩いスキーマ宣言（`{"type":"object"}` に `{}`）に
  よる E2 ゲームは完全には防げない。だから「vet402-l1-only ALLOW は開示付き・
  拒否可能」という**選択の構造**が防御で、完全性は主張しない。完全な防御は E3。

## 5. C1 リハーサルが見つけた欠陥（段3で同時に直す）

2026-08-26 のリハーサル（本番スコアAPIに対して SpendGuard 実走）で判明:
1. **SDK が誤 apiUrl で 404 を握りつぶす**: `createVouchClient({apiUrl:"https://vet402.com"})`
   のように origin を渡すと `/api/v1` が付かず、SDK は 404 を throw せずに
   **全フィールド undefined の body を返す**。結果 `Date.parse(undefined)=NaN` で
   fail-closed の `payee_score_stale` になる。統合者が黙って壊れる。
   → request で 2xx 以外を throw する / body に必須フィールドが無ければ throw する。
2. **stale の境界衝突**: 本番の payee キャッシュ TTL(5分) と SDK の
   `DEFAULT_MAX_SCORE_AGE_MS`(5分) が同値。キャッシュ末尾を引くと必ず stale。
   → SDK 既定を 10分へ（サーバ側 `/score` の maxDuration=30s と整合。両者を
   同値にしない）。
デモは**既定 apiUrl なら 2本立てが成立する**ことを本番で確認済み
（本1: カタログ4件すべて allow=false / 本2: 48/48売り手 allow=true）。
上の2つは「統合者が最初の5分でつまずく」罠なので、会期前に直す価値がある
（バグ修正＝凍結対象外）。

## 6. 3分野への波及（この設計が同時に効く理由）

- **堀**: E2 と mismatch がファシリテータ不可侵の固有データ。E3 の取水口は
  ETHOnline の payOrRefuse（attest は関数の一部と仕様済み）
- **エンジン**: 段1で判定を増やさず識別を増やし、段3で C-1/C-2 を塞いだ
  ALLOW を開ける
- **市場**: 「active 15,251 中 pass 1,246（8.2%）／実費で買った653件のうち宣言
  どおり届いた214件」——全数字 API 再現可能・誰にも反証されない楔


## 7. 競合の実地検証（2026-08-26・一次情報）と位置取り

本家 Third-Party Extensions の隣人4社を README・コード・npm・本番サイトで検証:
- **zauth**（monitoring/verification/refund SDK）: 売り手側の**自己監視＋自己返金**。中立でない。
  唯一の留保: サイトの「Provider Hub」が x402 エンドポイントへの live checks を謳う——
  自己資金で実決済まで通し決済を再読するかは一次仕様に到達できず**未確認**。将来の唯一の
  正面競合候補として監視する
- **OMATrust**: ID・アテステーション・レジストリ（買わない）
- **PEAC Protocol**: 発行者の**自己申告**レコード（作者自ら「独立に確立した事実ではない」と明記）。
  牽引は最強（GitHub star最多14・2025-07創設・組織後ろ盾・CI稼働）
- **x402r**: 返金エスクロー／仲裁（買わない・arbiterは売り手選定）。npm月間DLは最多612

**判定: vet402 の「実費で買い、決済をオンチェーン再読し、失敗も公開する独立検証者」は
一次情報の範囲で実質無二（確認）。** 4社に自腹購入検証は皆無。

**位置取り文（確定）**: 「vet402は、x402エンドポイントから自腹で実際に購入し、その決済を
オンチェーンで再読して失敗も証拠つきで公開する、唯一の独立検証者。売り手の自己監視でも
発行者の自己申告でも返金エスクローでもなく、それらの手前に必要な『独立に確立した事実』を供給する。」

**補完（競合でなく直交）**: x402r（vet402が失敗を実測公開→x402rが返金執行）が最優先。
次点でPEAC（測定値を可搬署名レコードへ封入）。将来の統合先候補。
