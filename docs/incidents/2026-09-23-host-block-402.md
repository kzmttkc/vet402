# 2026-09-23 — every URL answered 402 for 38 minutes (host block, not the payment gate)

**Window**: 2026-09-22 21:24:47 UTC → 2026-09-22 22:02 UTC (2026-09-23 06:24–07:02 JST). 38 minutes.

**What a visitor saw**: `HTTP/2 402` with `x-vercel-error: DEPLOYMENT_DISABLED` and the body
`Payment required`, on every path, including `/`, `/api/health`, `/observatory` and
`/api/v1/observatory/export.csv`.

**What it was not**: the 402 did not come from vet402's payment gate. The gate answers `402` with a
JSON x402 challenge; this was the host's own error page.

**Cause**: the Vercel team that hosts vet402.com was blocked for exceeding the free plan's fair-use
limit. The team API reported
`softBlock = {reason: "FAIR_USE_LIMITS_EXCEEDED", blockedDueToOverageType: "fluidCpuDuration", blockedAt: 1790112287240}`
and `billing.plan = "hobby"`. Three sites on that team answered 402 at the same time; a fourth,
on different infrastructure, stayed up.

**Fix**: the account moved to a paid plan at 2026-09-23 07:0x JST and the block cleared. Measured
after the change: `/`, `/api/health`, `/observatory` and the public export all answered 200, and
the claims canary read 60/60 true.

## What this did and did not do to the published record

- **No purchase row was lost.** No scheduled run fell inside the window. In the public export the
  last row before it is `2026-09-22T18:02:35Z` and the first row after it is `2026-09-23T00:00:06Z`,
  which is the next scheduled run, not a recovery. Anyone can recount from
  `https://vet402.com/api/v1/observatory/export.csv?days=2`.
- **The 12:00 UTC purchase run of 2026-09-22 was already complete** before the block (120 settled
  that UTC day).
- **Reading the export during those 38 minutes returned 402**, so a third party reproducing the
  numbers in that window saw the host error rather than a CSV. Outside the window the same request
  returns the same rows; the data was never rewritten.
- Nothing in `/corrections` changed. That log records corrections to measurements. This was an
  availability failure, and no measurement moved.

## What changed after it

- The daily `index-feedback` cron went from four runs to two (commit `cf16f31`). Base produces about
  43,200 blocks a day and each run covers 400,000, so two runs twelve hours apart still see every
  event.
- The uptime probe now reads `x-vercel-error` when it sees a 402 and names the host block in the
  alert, instead of reporting `health http 402` (commit `7be904a`).
- The same probe reads the team's plan and block state every run, so a block or a downgrade is
  named before a visitor meets it (commit `59ce090`).
