## 2. 監査がグラントに効く4点（重要度順）

### ① S-4「証拠層の崩れ」は、我々が申請で書いている文そのものに当たる（最優先）

提出済みの Base 指名（8/25）と Octant intake（8/27）、公開中の `/demo`（9/3収録）は、いずれも
**「settled の各行に on-chain の受領証が付く。誰でも検算できる」**を中心に据えている。
監査の実測は `settlement_verified=true` 1,629 行のうち **1,558 行（95.6%）が `auth_nonce` 束縛なしの旧判定**。
使い回しの痕跡は無い（tx 重複 0・決済時刻は全 1,589 行が認可窓 −1〜+62 秒）が、
**強い行と弱い行が公開面で区別できない**。

グラント審査は「主張が検算できるか」を見る。第三者が監査記録（公開リポにある）に当たれば、
**我々自身が「95.6% は弱い」と書いた文書**と、我々の申請文が並ぶ。ここは早いほど良い。

**お願い**: S-4 の是正で公開面に**2層**を出すとき、`state` / endpoint 記録頁 / `/api/v1/observatory/decisions` の
**どのフィールドで層が読めるか**を教えてほしい。こちらは申請文と `/demo` の字幕を、その語彙に合わせて直す。
無実の売り手を `refuted` にしない方針（監査 §5 S-4）はグラント側も支持する。

### ② 名乗りの分裂（S-6）は「検算できる会社」の入口で漏れている

本番の署名本文が `Vouch verified payee registration` で始まる（実測）。申請文・npm・サイトは `vet402`。
**我々を検算しに来た人が最初に触る画面で、サイトに存在しない名前に出会う。**
S-6 の是正（1行目を `vet402.com — <purpose>`・`domain:` 行必須）は、セキュリティ対策であると同時に
**申請の信頼性そのもの**。優先度を落とさないでほしい。

### ③ census が「30d」と名乗るのに索引範囲を開示しない（9/3 発注・未着手）

`/api/v1/census/summary?window=30d` は `window: "30d"` を返すだけで、実際にどこまで索引済みかを返さない。
**いまグラント側の最強の一枚は「実需 379,748 件・支払元 3,890」**だが、**この一枚を申請に書けないでいる**。
分母を売る会社が分母の期間を偽ることになるため、計器から外して凍結している。
`indexed_since`（チェーン別の最古 observed_at）を1フィールド足すだけで解ける。**費用対効果はこの中で最大。**

### ④ 監査そのものが、これから出す申請で使える資産になっている

4日で3本（9/2 敵対監査・9/4 第2回・9/5 セキュリティ＋CIA＋レッドチーム）、記録は公開リポにあり、
S-1 キルスイッチは**同日に本番実証**、CT監視とオフボックス台帳スナップショット（復元実証つき）も同日導入。
**「測る側が自分を測り、悪い結果ごと公開する」**は、Octant が L2BEAT / growthepie に配った理由そのものである。

**提案（実装はそちらの判断で）**: 監査の要約を1枚、公開面に出す（`/accuracy` から辿れる形が自然）。
可用性 97%・障害3件・最長10h36m の原因未記録も**そのまま載せる**。隠すと資産にならない。
出たらグラント側が申請文とアウトリーチに載せる。
