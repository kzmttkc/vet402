
### Questions

### What is x402?

x402 is an HTTP 402 payment protocol for AI agents. A server answers 402 with payment terms, the caller pays on chain, often in USDC, and retries the request with proof of payment.

https://vet402.com/x402
https://vet402.com/blog/what-is-x402

### How do AI agents pay with stablecoins over x402?

An AI agent pays an x402 API with a stablecoin by answering HTTP 402. The server returns payment terms that name an asset, often USDC, plus a network, an amount, and a recipient. The agent signs that transfer and retries the request with proof of payment.

https://vet402.com/x402/stablecoin-payments

### How do you check an x402 seller before paying?

Check an x402 seller before paying by reading the purchases vet402 has made from that seller and the decision those purchases support. The decision names the terms of the last purchase whose delivery vet402 confirmed. If the 402 in hand names a different recipient, asset, network, or scheme, or a higher amount, that offer is different from the one that was delivered. The amount is in 6-decimal ledger units: multiply it by 10^12 on BNB Chain and by 10 on Stellar before comparing.

https://vet402.com/x402/check-a-seller

Under x402's exact scheme a settled payment is final, and proof of payment exists on-chain. A buyer still has no way to see, before paying, what a seller delivered. vet402 answers that with records of real purchases. Registries can be written for cents and directory metrics can be manufactured, so vet402 does not take either at face value. It measures, states which level of verification a result came from, and says "unverified" when it has not measured. Nothing on the site is presented as an estimate.

Formerly named "Vouch". Renamed to vet402 in August 2026. The production URL is `vet402.com`. The GitHub repository is `vet402/vet402` (the older `kzmttkc/agent-trust` URL still redirects there. Cite the new one). Issued API keys and webhook headers keep the `vouch_` / `Vouch-` prefixes for backward compatibility. The old name appearing there is deliberate. It is not stale documentation.

### Verification levels

Every word used below is defined in one sentence each at https://vet402.com/observatory/methodology#vocabulary, and the same definitions are published as `DefinedTermSet` structured data on that page and in https://vet402.com/llms-full.txt.

This is the published methodology. A result is labelled by the level that produced it and never moves up a level. An L0 probe cannot report settlement, and an L3 opinion is never folded into an L0 to L2 fact. L0, L1 and L2 verdicts ship live in the observatory (see "Implemented and live" below). L0 and L1 are full measurements. L2 is a deliberately minimal structural check. It parses the response as JSON and confirms the seller's own declared required keys are present, nothing deeper, as described on https://vet402.com/observatory/methodology. L3 is not built and no opinion is published anywhere on the site.

- **L0 Liveness**: does the endpoint answer correctly? Probe, no purchase. Output: pass / fail / unverified.
- **L1 Settle-through**: does the payment settle, and does a non-empty 2xx come back? Real purchase. Output: n of m settled, n delivered, latency. settled = the transfer re-read on-chain. delivered = settled AND the paid request answered 2xx other than 202 Accepted, with a non-empty body.
- **L2 Conformance**: does the response match the seller's own declaration? Purchase plus machine diff. Output: match / mismatch / no_declaration / not_checked.
  Decision and facts documents store conform, mismatch, undeclared, or not_checked: conform is written when the re-read L2 value (l2_reading) of the latest delivery is match, mismatch is written when that re-read value is mismatch (an older mismatch row with no recorded reason is re-read first, and a cut body reads not_checked), and in the other cases the decision word is not_checked when the current declaration names output (a required key or an example property) or when the purchase row of the latest delivery recorded a declaration and its re-read value is not_checked, and undeclared when neither holds; the latest delivery is read at any age, so a mismatch holds until a later delivery replaces it.
- **L3 Quality**: is the content any good? Not built. No L3 opinion is published.

What the API returns today is a different, older thing. It is a 0 to 100 trust or payee score banded ALLOW / WARN / BLOCK. It predates the levels and stays available to API and SDK callers during the transition. Observatory verdicts replace it as they ship, and a score is never reported as an L0 to L2 result. The front page states this relationship in §2.1. Scoring is fail-closed. An input that could not be read is never reported as an input that was checked and found fine. Such a verdict is marked `degraded`, is not cached, and returns BLOCK to callers, while the public profile pages say "Not verifiable right now" instead of publishing a number.

### API: no key required

These are open paths, rate-limited per IP. Nothing below needs an account. Every response on the JSON read paths and the CSV exports carries `RateLimit-Limit`, the ceiling for that path. `RateLimit-Remaining` and `RateLimit-Reset` are per-caller, so they are sent only on responses a shared cache does not replay to someone else, chiefly the `429`, which also carries `Retry-After`. A cached `200` deliberately omits them rather than handing you a counter that belongs to whoever populated the cache. A path under `/api/` that matches no route answers `404` as JSON (`{"error":"not_found","path":...}`), never as an HTML page.

- `POST /api/v1/payment-proof` reads one seller PAYMENT-RESPONSE header (base64 JSON with success, transaction, network and payer) or a network plus a transaction hash. vet402 reads that transaction again on Base, Celo, Arbitrum One, Avalanche C-Chain, BNB Chain, Solana, Arc, Tempo, XRPL and Stellar and returns found, network, tx, block, from, to, asset, amount in atomic units, status, explorer and as_of. A chain outside that set comes back as unsupported_network. Keyless. 20 requests a minute per IP. The chain read stops at 8 seconds. This route does not pay and does not sign.
- `GET /api/v1/erc8004/check` reads one ERC-8004 Reputation Registry feedback on Base (`chain=eip155:8453`), fetches its feedbackURI JSON, re-reads payment evidence from proofOfPayment or vet402 weekly `transactions[]` (checks.proof_source), and returns verdict (verified, verified_payment_unlinked_client when payment evidence holds but the payer cannot be tied to the EVM writer e.g. cross-chain payers—not a demerit, payment_recipient_unverified when the recipient of the payment is neither confirmed nor contradicted, mismatch with reasons, no_proof, unreadable) with check fields. Pass agentId and client or feedbackIndex. Keyless. 30 requests a minute per IP. Results cache 30 minutes. No on-chain writes.
- `GET /api/v1/accuracy` — the accuracy ledger as JSON. `slo.l1_probe_error_rate_pct` is the share of all L1 attempts in the last 7 days whose purchase run did not complete inside vet402 (`request_error` / `in_flight`, counts in `slo.l1_7d`); it is not the held share of the ledger export (`slo.l1_7d.held` of `slo.l1_7d.signed`) and not the "vet402's side" column of /sellers, which classifies each listed Base listing by its latest attempt of any date. Aggregate counts, and the same numbers /accuracy renders **with the same caveats attached**: the `interpretation` object carries the notes that qualify each rate — that a benchmark "detection" counts BLOCK *or* WARN and how many known-bad addresses stopped at WARN, that a 0% false-positive rate means "none were blocked" rather than "all were passed" and how many known-good addresses only reached WARN, and that a rate below the minimum sample is `null` rather than a number. The older score endpoints below need the same key. They return the transitional 0 to 100 score described at the top of this file (deprecated. The decision document above is the current integration) and the operational calls around it. Since 2026-09-29 each score response says so itself: `deprecated: true`, a `deprecation` object naming the decision endpoint to use instead, and the `Deprecation` / `Link` headers. The score's value is unchanged, and it rates a wallet or agent as a whole, so it can read ALLOW where the decision for one endpoint paid to that wallet reads WARN or BLOCK. Decide with the decision endpoint.

- `GET /api/v1/payees/{address}/score` — the buyer-side question: should this payee be paid?
- `GET /api/v1/wallets/{address}/score` — trust score by wallet address (the path x402 middleware uses)
- `GET /api/v1/agents/{agentId}/score` — trust score by ERC-8004 agent ID (optional `?wallet=` verifies the registered wallet; optional `?chain=` selects an enabled chain, default Base)
- `POST /api/v1/scores/batch` — score up to 25 agents in one request
- `GET /api/v1/agents/{agentId}/history` — score history snapshots (paid plans)
- `POST /api/v1/payments/x402` — attest an x402 payment settlement after verification (idempotent on txHash)
- `POST /api/v1/events/{trustEventId}/outcome` — report what actually happened after a verdict; this is what the public accuracy ledger is computed from
- `GET|POST /api/v1/watchlist`, `DELETE /api/v1/watchlist/{id}` — watch an agent or wallet; verdict changes arrive as a `watch.verdict_changed` webhook
- `GET|POST /api/v1/webhooks`, `DELETE /api/v1/webhooks/{id}` — webhook subscriptions

- `GET /api/v1/observatory/state` — the aggregate snapshot. Carries `license`, `licenseUrl`, `retrievedAt` and `cite` in the body. Top-level totals include testnets; `byChain` is mainnet-only (`byChainScope`), so `sum(byChain)` can be below `totalEndpoints`. `publishedPass` counts endpoints on record whose latest L0 probe passed, including delisted endpoints, so it can exceed `activeEndpoints`; `publishedPassActive` is the part on active records, and `publishedPassActiveProbeOlderThan7d` the part of that last probed more than 7 days ago. `l1.endpointsSettled` (endpoints with a settled row, active or not) is `l1.endpointsSettledSellerReceipt` (at least one transaction the seller named in its receipt) plus `l1.endpointsSettledIndexOnly` (every settled transaction found by vet402's own settlements index, or named in a Circle Gateway batch (settlement_source=circle_gateway); no seller receipt). `adoption` (since 2026-11-08) is use by others, each figure with its period, read time and source: `sdkDownloads` (npm's last-month window for @vet402/sdk) and `keyedDecisionCalls` (the monthly values of /api/v1/usage/monthly for key owners outside vet402). A figure that cannot be published is left out.
- `GET /api/v1/observatory/history` — the daily series per chain.
- `GET /api/v1/observatory/delivery.csv?days=90`: one row per settled purchase with the three delivery values (`delivered`, `no_body_observed`, `not_established`), raw fields to re-count, and `observed_at`. Key-less, 6/min, cached up to 3 hours (see Freshness). Methodology: https://vet402.com/observatory/methodology#delivery-values
  - `body_bytes` is empty on settled rows up to 2026-09-29 06:01 UTC, from before vet402 logged the response size. Read an empty value as not recorded. It does not mean zero bytes.
  - `payer` is the wallet that signed. On Solana that is the wallet owner, and the SPL transfer leaves from its associated token account, so compare the payer with the owner of the transfer's source account.
- `GET /api/v1/observatory/export.csv?days=90` — the L1 purchase ledger, one row per attempt that reached a decision. Without `days` the window is the last 90 days (`days` takes 1 to 366). The ledger starts at 2026-08-14T09:54:31Z, so from 2026-11-12T09:54:31Z the default window no longer reaches its first rows: use `?days=366` for the whole ledger. Paid attempts are the rows with status settled, settle_failed, delivered_no_receipt, settle_claimed, settle_claimed_unverifiable or settle_claim_refuted (their count is `l1.attempts`); the other rows stopped before signing, with `spent_units` 0 and a blank `network`. A settled Circle Gateway row has a blank `tx_hash`, and its batch transaction is kept beside the row. Columns are only ever appended. `held_reason` says why a row is held (vet402's hold) rather than counted against the seller; it is empty on a row awaiting on-chain verification (`settle_claimed`), which is a different state (counted as `l1.awaitingReread` on `/api/v1/observatory/state`, not in `l1.inconclusive`). `request_body` says what the paid request carried: `declared` (the body the seller's own 402 declares, since 2026-09-17), `empty` (`{}`) or `none` (no body, recorded since 2026-09-20); blank means no record, not `empty`. `request_body_sha256` is the SHA-256 of the bytes sent on `declared` rows since 2026-09-20; the body itself is not republished. `settlement_source` says who named the transaction: `seller_claim` (the seller's settlement receipt), `vet402_index` (no receipt came back and vet402's own settlements index found the transfer), or `circle_gateway` (a Circle Gateway batch transaction kept beside the row). This value is absent while the Arc Gateway lane flag is off. `request_query` says which URL the paid request went to: `declared` (the query arguments the seller's own 402 declares, appended to the listed URL as declared; recorded on the row since 2026-09-20 and published as a column since 2026-09-21, on the networks in vet402's per-network allow-list), `empty` (the seller declared none) or `refused` (a declaration was there and vet402's rules did not use it). A declared name the listed URL already carries is dropped on its own and the other pairs are still appended, so a collision yields `refused` only when nothing is left to append. Blank means no record — a network the allow-list does not name, a Tempo row, a row that ended before a paid request, or a row before 2026-09-20 — and the column alone does not separate those. `request_query_sha256` is the SHA-256 of the appended pairs as one form-urlencoded string on `declared` rows; the query string itself is not republished, and the hash is for matching rather than a way of hiding it — the names and values are the seller's own and the 402 that answered the unpaid request is where they were read from. `spent_units` is the amount vet402 signed for on the attempt (what it put at stake), not an amount shown to have moved: a `settle_failed` row with no transaction still carries the price there. `confirmed_units` (since 2026-09-29) is the amount vet402 re-read on-chain as transferred: `spent_units` on `settled` rows and `0` on every other row, including `settle_claimed` rows still awaiting the re-read; `0` means no confirmed transfer, not a transfer shown not to have happened. `purchase_id` (since 2026-09-29) is the purchase's id, the `subject_id` of its rows in `/api/v1/observatory/corrections`. `l2_reading` (since 2026-09-29) is `l2_schema` read again with today's rules, the value the record page and the decision use; `l2_schema` keeps the value recorded at the time.`response_sha256` and `response_bytes` (since 2026-11-24) are the SHA-256 and byte length of the paid response body vet402 read; the body itself is not republished; blank means no record and `0` on `response_bytes` means an empty body was read. Filled only when vet402 read the paid response body through to the end (not when the read hit the cap or stopped partway). Optional `?include=erc8004_agent` (since 2026-11-17) appends `erc8004_agent`: the CAIP agent id `eip155:8453:{agentId}` when the row's pay_to exactly matches an owner or agentWallet in vet402's Base ERC-8004 index, blank otherwise; the default export without that query keeps the frozen 21 columns. `scripts/declared-body-before-after.mjs` in the repository recomputes the before/after 2xx rate of the declared body from this CSV alone. Licence, retrieval time, row count and window are in the `x-vet402-*` and `Link` response headers, because a CSV has nowhere to put a comment.
- `GET /api/v1/observatory/l0/export.csv` — the latest public L0 verdict per endpoint (since 2026-09-29): one row per endpoint on record, active or not, excluding endpoints paying vet402's own addresses — the data behind the L0 counts of `/api/v1/observatory/state`. Columns: `endpoint_id`, `resource_key`, `network`, `chain`, `network_class` (`mainnet` | `testnet` | `unclassified`), `listed`, `published_verdict` (`pass` | `fail` | `withdrawn` | `unverified`; `withdrawn` means the newest 2 probes failed on a route absent from a complete catalog fetch, left out of the public L0 fail count), `latest_probe_verdict`, `last_probed_at`, `latest_probe_older_than_7d`. Counting `published_verdict=pass` gives `publishedPass`; `network_class=mainnet` rows grouped by `chain` give `byChain`. 6/min, cached up to 45 minutes (see Freshness); definitions in `x-vet402-column-notes`, retrieval time in `x-vet402-retrieved-at`
- `GET /api/v1/sellers/export.csv` — the /sellers classification (since 2026-09-29): one row per active Base listing (records opened for a seller's re-test request included), classified by its latest purchase row with the same function /sellers uses, so counting rows by `outcome` (`delivered` | `pending` | `seller` | `vet402` | `unsorted` | `not_bought` | `not_tried`) gives the page's totals. Also `fix_mode`, `side_label`, `confirmed_seller`, `held_reason`, the latest row's time, status, network, HTTP status and `purchase_id`, `in_ledger_export`, and `attribution_review` (`under_review` on seller rows). Served noindex, like the page, while its attribution is under review. 6/min, cached up to 45 minutes (see Freshness)
- `GET /api/v1/judgments/{file}`: daily judgments JSON (`index.json`, `index-{00..ff}.json`, `{resource_id}.json`), key-less, no IP cap, cached at the CDN until the next UTC day, CC-BY-4.0

### Packages

The unscoped `vet402` package on npm bundles `@vet402/sdk` and `@vet402/middleware` for one install (`npm install vet402`, with buyer exports under `vet402/buyer` and seller under `vet402/seller`). To install pieces separately, use `@vet402/sdk` (spend guard), `@vet402/middleware` (x402 request gate), or `@vet402/mcp-server` (local MCP tool). All come from the same repository. The SDK and the middleware both default to fail-closed: only an ALLOW passes, and a WARN, a BLOCK, a degraded verdict, or a partially measured one is denied unless the caller explicitly opts out.

### Implemented and live

- Address control verified: prove control of a wallet by signature, get a public page and an SVG badge
- Drop-in x402 middleware, REST API, and MCP tool
- Public accuracy ledger, published with no pressure to flatter vet402
- The x402 Observatory: L0 liveness probes on a rolling schedule over the public discovery catalog, which have not reached each listing (coverage7d and the L0 export say which), multi-chain (see /observatory/state for the breakdown), with delisting alerts for claimed sellers. L1 settle-through: real purchases of that chain's pinned asset (USDC on Base, Arc, Celo, Solana, Stellar, Arbitrum One and Avalanche C-Chain, USDC.e on Tempo, RLUSD on XRPL, USD1 on BNB Chain) on the chains whose payer lane is switched on (the chains reached so far, with their counts, are the `l1.byChain` rows of https://vet402.com/api/v1/observatory/state), budget-capped, one purchase per endpoint per sweep window, recording each settlement and each refusal. vet402 may reserve one paid test of a listing in a UTC date window; the list lives in src/lib/observatory/pinned-purchases.ts and sellers cannot pay or ask for entries on it. L2 is a minimal structural check of the response against the seller's own declared schema

### Use cases

- x402 API providers deciding whether to accept a payment from an unfamiliar agent wallet
- Spending agents checking a counterparty before initiating a machine-to-machine payment

### Chain

Base (ERC-8004 agent identity / reputation) is the default and the chain the scoring API measures on. The agent-score endpoint accepts `?chain=` to select another enabled chain. An unknown or disabled chain is a 400 with the live list, never a silent fallback to a different chain.

The observatory is a separate system and is not Base-only: L0 probing runs on a rolling schedule over the public x402 discovery catalog and has not reached each listing or chain yet, and https://vet402.com/observatory/state reports the current per-chain breakdown. L1 purchases run on the chains whose payer lane is switched on. The chains they have actually reached, with their counts, are the `l1.byChain` rows of https://vet402.com/api/v1/observatory/state, and that list is the one to read rather than any list written out here. Settlement is re-read on-chain with a chain-specific binding back to the signature vet402 holds: on Base, Arc, Celo, BNB Chain, Arbitrum One and Avalanche C-Chain the EIP-3009 authorization nonce, on Solana a memo vet402 wrote itself, on Tempo the indexed memo of a TIP-20 `TransferWithMemo`, on XRPL the hash of the signed blob. The settlement asset is USDC on Base, Arc, Celo, Solana, Stellar, Arbitrum One and Avalanche C-Chain, USDC.e on Tempo, RLUSD on XRPL, and USD1 on BNB Chain. Stellar is re-read for payer, payee, amount and asset, and is published as amount and payee. A purchase on a chain with no re-reader stays at `settle_claimed`. It is never silently paid on a substitute chain.

### Corrections

If a published score or verification result about a wallet you control is wrong, there is a free, key-less correction route open to anyone, customer or not. See section 8 of https://vet402.com/legal/terms#corrections

Corrections that are issued are published at https://vet402.com/corrections, and as JSON at https://vet402.com/api/v1/observatory/corrections. Read the count from there rather than from this file: it is not zero (the first corrections were published on 2026-09-04), and a number written here goes stale the next time vet402 corrects something.
